一、五层单向依赖架构

依赖严格自上而下单向流动。core_engine 为无 Qt 的纯逻辑共享层，已 vendor 进 ClickOCR 目录实现自包含分发。

关键约束：onnxruntime-gpu 与 onnxruntime-directml 在 PyPI 上互斥（同为 onnxruntime 导入名），必须分 venv——这直接决定了「CUDA 版 / DML 通用版」两条独立构建线无法合并为一份产物。

二、主识别数据流（核心闭环）

从全局热键到文字上屏的完整链路。注意线程边界：抓屏与渲染在 UI 线程，推理在常驻工作线程，写库在 UI 线程回调。

为什么 worker 必须常驻（本期最重要的变更）：onnxruntime 的 CUDA EP 会为每个新建线程分配 thread-local 的 CUDA stream / cublas·cudnn handle / workspace，实测约 188 MiB/线程且线程结束后不回收。旧实现每次截图 new OcrWorker → 新线程 → 显存逐步累积，连续截图若干次后 8GB 显存耗尽。
现为单线程常驻 + 任务槽：submit(task_id, img) 直接覆盖未取走的旧任务（天然丢弃过期任务），CUDA workspace 只分配一次，显存稳定；TableWorker 出于同一原因同样常驻。

三、次级数据流

主闭环之外的六条独立链路，各自有明确的触发条件与失效边界。

四、数据模型（SQLite）

建库时一次性建齐 11 张表 + 1 张 vec0 虚表。当前仅 screenshot_history 在实际使用，其余为空转预置（未启用）。

在用表：screenshot_history 的两个关键语义约定
① ocr_boxes 三态（决定「打开历史图是否补识别」）
值含义打开历史图时
NULL从未识别ocr_auto 开 → 立即识别回填；关 → 不动
'[]'已识别、无文字直接用，不重跑模型
'[...]'已识别、有文字直接显示
② model_tier / device 是「执行记录」而非配置快照
字段语义
model_tier这条实际用的档位 tiny/small/medium；未识别 = ''
device这条实际生效的设备 cpu/cuda/dml；未识别 = ''
写入时机INSERT 留空；唯一写入点是 update_ocr()（识别刚跑完）
为什么用空串而不用 NULL：model_tier TEXT NOT NULL，而 SQLite 删不掉 NOT NULL（需重建表 + 重建 FTS 触发器/索引），且全项目 init_db() 只有 CREATE TABLE IF NOT EXISTS、零处 ALTER TABLE → 空串是零迁移方案。'' 与 ocr_boxes IS NULL 严格一一对应（同一判据，不会各说各话）。
表状态用途与关键字段
screenshot_history 在用 历史记录主表。screenshot_path（相对路径）· ocr_text（QR 以 [QR] 前缀行并入）· ocr_boxes（三态，含 kind）· model_tier / device（执行记录）· is_favorite（不受 FIFO 限制）· annotations · has_table · status（0=未向量化）。4 个索引
images M3 预置 图片主表，主键为 file_path+size+mtime 哈希。含 EXIF 全字段（相机/光圈/曝光/ISO/焦距）与 GPS（经纬度/海拔/国家/城市）
image_ocr M3 预置 每行文字一条（RAG 天然 chunk）。text_content · polygon_json · confidence · model_tier
image_tags M3 预置 三源标签：manual / ocr / ai，联合主键 (image_id, tag)，NOCASE 排序
image_ocr_extend M4 预置 区域框选重识别结果（region_x/y/w/h + ocr_texts），级联删除
image_search FTS5 虚表 trigram 分词全局搜索，聚合 OCR/caption/tag 三源。4 个触发器自动同步（ocr 增删、caption 更新、tag 插入）
table_cache M4 预置 表格识别结果缓存（table_result JSON，按 image_id+model_tier 索引）
image_embedding 未启用 向量元数据（预留，未启用）
image_embedding_vec vec0 · 未启用 sqlite-vec 虚表 vec0(embedding float[512])。按扩展可用性在 Python 层动态创建，缺失则降级跳过
image_hash M4 预置 感知哈希去重（phash / dhash / ahash），主键 (image_id, hash_type)
image_layout 可选 DocLayout-YOLO 版面分析结果（layout_json）

五、跨切面关注点

贯穿各层的横切机制——这些是理解代码行为的隐性契约。

单实例

QLocalServer 监听 ClickOCR-SingleInstance；二次启动检测到已存连接则发 b"show" 唤醒已有实例并退出，避免双开抢占全局热键。

线程模型（常驻复用）

4 类 QThread，其中 OcrWorker / TableWorker 为常驻单线程 + 只认最新任务；EngineLoader 后台加载；ScrollWorker 按需。UI 线程全程不阻塞。

引擎容错

引擎初始化/加载失败 → engine=None + 非阻塞告警弹窗，程序继续运行：截图、贴图、标注照常可用，仅文字识别停用。

懒加载策略

ocr_keep_alive=true（默认）后台线程预加载；false 则首次识别才构建，启动省 200–400MB。模型热切换 switch_model() 只换内部引擎，包装对象不变。

主题与文案外置

明/暗/跟随系统 + install_system_follow 运行时切换；全部 UI 文案走 ui_text.json（274 条）的 T()，缺失回退默认值；SVG 图标按需着色。

窗口配额

三类独立配额：贴图 max_history_windows=1、历史图 max_hist_windows=3、钉图 max_pin_windows=5（上限 20）。超限从最旧回收。

FloatGroup 浮窗管理

收口 z 序（raise_all）、绘制让位（maybe_yield，事件驱动替代 80ms 轮询）、位置跟随（follow）——消灭散落的手动 raise_。

NUMA 亲和

多 NUMA 节点时把进程绑到节点 0：Windows 用 GetLogicalProcessorInformationEx + SetProcessAffinityMask/SetThreadGroupAffinity，Linux 读 /sys + sched_setaffinity。单节点零开销。

配置实时读取

App.ocr_auto 实现为 @property 每次读配置，而非 __init__ 缓存 —— 设置保存后同会话立即生效。回归脚本含静态防线检测「@property 与 self.X= 冲突」。

六、可扩展性设计

四个正交的扩展方向，以及三个已被识别的缺口。

换引擎

Protocol 契约 + 单一注入点。新增一个满足 recognize/get_info/switch_model 的实现类，改 app.py 一处构造即可。业务层与 UI 只依赖 OcrBox 与 Protocol。

加加速后端

在 DEVICE_PKG / _EP_HINT 两张表登记即可，UI 自动出现选项（available_devices() 不过滤未装项，保留用户选中后触发检测）。

加标注图元

新增一个 _BaseElement 子类 + 在 _ItemFactory 注册；若要可撤销，再加一个 _Cmd 子类，无需改动撤销栈逻辑。

加图标

放入 resources/icons/ 的 SVG 即可，运行时着色 + 缓存，无多分辨率位图成本。

数据层前瞻

建库即建齐 11 表 + vec0，后续 不需要 schema 迁移：图库与去重的落点均已预留。

缺口：热键无抽象

HotkeyHost 强绑 Win32 RegisterHotKey + nativeEvent，是 Linux / Wayland 移植的首要改造点。

缺口：「操作 UI」清单手工枚举。_all_float_windows() 逐类收集需要隐藏的窗口（各 overlay 的状态栏/工具栏、历史面板、设置面板、表格面板）——新增一类浮窗必须同步改这个方法，否则新窗口会入镜。

七、性能设计

按「资源占用 → 推理调优 → UI 响应」三个层面收敛。

内存与显存
worker 常驻复用防显存泄漏：CUDA EP 每线程 ~188MiB 不回收
引擎懒加载ocr_keep_alive=false 时启动省 200–400MB
表格模型用后即卸SLANet 不常驻，省 150–200MB（模型本身仅 ~6.8MB）
缩略图 160px列表加载快、磁盘占用小
FIFO + 收藏豁免history_max_count 默认 3000，避免无限增长
窗口配额回收贴图 1 / 历史图 3 / 钉图 5
CPU 与 GPU 调优
intra_op_num_threads= 单 NUMA 节点物理核数，避免 ORT 默认用满逻辑核导致超订
inter_op_num_threads走 ORT 默认
NUMA 亲和多节点绑节点 0，规避跨节点访存；单节点零开销
探测输入 640×640接近真实 det 负载；用 320 会低估 GPU 收益导致误拒
验证真用 GPU不存在的卡 ORT 会静默回退 CPU，必须查 get_providers()[0]
DML 选卡monkeypatch get_ep_list 注入 device_id
UI 响应性
模型后台加载EngineLoader 在原生层释放 GIL，加载期间 UI 完全不卡
抓屏延时 60ms等遮罩彻底消失，避免把遮罩拍进去（正确性优先于延迟）
绘制让位事件驱动由宿主 mouseMove 触发，替代固定 80ms 全局光标轮询
只认最新任务连续截图时自动丢弃过期任务，不做无效推理
实测加速比：CUDA（v6-medium det）7.54×（149.5ms → 19.8ms）；DML 同机 6.58×（155.8ms → 23.7ms），且 DML 能额外吃下设备 1（2.37×）。两者几乎持平，故 DML 通用版作为默认分发形态——通吃 AMD/Intel/NVIDIA，无需用户按显卡选包；CUDA 版仅作 NVIDIA 极致性能的可选项。

八、安全设计

桌面端的安全模型是「完全离线、无鉴权面」，因此重点在数据隐私、输入健壮性与系统集成边界。

核心保证：运行期零网络。对全部源码（app.py / config.py / hotkey.py / main.py / ocr/ / ui/ / core_engine/ / screenshot/）检索网络 API（requests. / urllib / http(s):// / socket.），唯一命中是 ort_runtime.py 里 MIGraphX 的 pip -f 索引参数，且仅在开发模式下由用户显式点「安装」才使用；打包版无 pip，直接返回提示。
即：模型随包 bundle、无遥测、无更新检查、无云端同步，截图内容不会被上传。

数据本地存储与隐私边界

截图、缩略图、SQLite 元数据（ocr_text / ocr_boxes / annotations）、日志全部明文落本地，工具本身不做加密。

  • 风险提示：截图常含敏感信息（身份证/合同/聊天记录），OCR 文本同样明文入库 → 安全性依赖 OS 账户隔离与磁盘加密
  • 缓解：history_max_count 限制存量；screenshots_dir 可指向受控目录；收藏便于自主管理

系统集成边界

  • 单实例：QLocalServer 本地命名管道，非网络端口
  • 热键：用 RegisterHotKey 由系统分发，不安装键盘钩子（不监听任意按键、不记录击键）
  • 点击穿透：仅用户显式触发，随时可撤销
  • 开机自启：写 HKCU（当前用户级），无需管理员权限，不改系统级配置
  • 打包版不自动联网装包

文件路径与文件名安全

  • 文件名替换非法字符 [\\/:*?"<>|\r\n\t] → _，同时阻断路径穿越（../ 中的 / 被替换）
  • 扩展名白名单：仅 png/jpg/jpeg/bmp/webp，非法回退 png
  • 质量参数钳制在 1..100
  • 删除用 missing_ok=True，仅删记录关联文件

输入健壮性（防崩溃）

  • 损坏/非法图片 → decode_image_bytes 返回 None，调用方跳过，不抛异常
  • pillow_heif 缺失 → HEIC/HEIF 静默不可用，不影响其它格式，不在导入期抛异常
  • core_engine 缺失 → 退化到 cv2 原生解码
  • 模型缺失 → engine=None + 弹窗，程序继续运行
  • 数据库异常 → 捕获返回 False
剪贴板边界：「点字复制」写入系统剪贴板（明文，任意前台程序可读）。这是截图 OCR 工具的固有属性而非缺陷，但用户应知晓：复制的敏感文本会进入剪贴板历史（若系统或第三方剪贴板管理器开启）。

九、构建线与运行时矩阵

两条构建线源于 onnxruntime 包的互斥性；EP 能力按平台分化。

构建线环境 / spec产物
DML 通用版 .venv-dml（onnxruntime-directml 1.24.4）
ClickOCR_dml.spec		 推荐分发 490MB / 382 文件 · ~70s
CUDA 版 .venv（onnxruntime-gpu 1.28.0）
ClickOCR.spec		 NVIDIA 最优 ~1.9GB
纯 CPU 版 已废弃 ClickOCR_cpu.spec 路线无效——从 gpu 包剔 CUDA 库永远得不到 DML
平台EP 选项说明
Windowscpu · cuda · dmlDML 通吃 AMD/Intel/NVIDIA DX12（WDDM 2.4+）
Linuxcpu · cuda · migraphx · openvino无 DirectML；AMD 走 MIGraphX（ROCm 6.4+），Intel 走 OpenVINO
打包版已捆绑运行时，EP 不可用即判定为设备/驱动不支持并自动回退 CPU；开发模式可 pip 自动换包。
DML 构建的配置覆写（关键）：resources/config.ini 是 CUDA / DML 两份构建共用的同一个文件（值为开发机的 cuda）。若不覆写，DML 包内只有 DmlExecutionProvider，rapidocr 告警后静默回落 CPU，DirectML 形同虚设。因此 ClickOCR_dml.spec 在打包时把 ocr_device 覆写为 dml 再打进包（写临时目录后作 datas 单文件项），源码 config.ini 一个字不改 → CUDA 版与开发环境不受影响。
