一、五层单向依赖架构

依赖严格自上而下单向流动。core_engine 为无 Qt 的纯逻辑共享层，已 vendor 进 ClickOCR 目录实现自包含分发。

关键约束：onnxruntime-gpu 与 onnxruntime-directml 在 PyPI 上互斥（同为 onnxruntime 导入名），必须分 venv——这直接决定了「CUDA 版 / DML 通用版」两条独立构建线无法合并为一份产物。

二、主识别数据流（核心闭环）

从全局热键到文字上屏的完整链路。注意线程边界：抓屏与渲染在 UI 线程，推理在工作线程，写库在 UI 线程回调。

三、次级数据流

主闭环之外的六条独立链路，各自有明确的触发条件与失效边界。

四、数据模型（SQLite）

建库时一次性建齐 11 张表 + 1 张 vec0 虚表。当前仅 screenshot_history 在实际使用，其余为 M3–M6 预置。

表状态用途与关键字段
screenshot_history 在用 历史记录主表。screenshot_path（相对路径）· ocr_text · ocr_boxes（JSON，含 kind=ocr/qr）· model_tier · device · is_favorite · annotations · has_table · status（0=未向量化）。4 个索引覆盖时间/文本/收藏/状态
images M3 预置 图片主表，主键为 file_path+size+mtime 哈希。含 EXIF 全字段（相机/光圈/曝光/ISO/焦距）与 GPS（纬度/经度/海拔/国家/城市）
image_ocr M3 预置 每行文字一条（RAG 天然 chunk）。text_content · polygon_json · confidence · model_tier
image_tags M3 预置 三源标签：manual / ocr / ai，联合主键 (image_id, tag)，NOCASE 排序
image_ocr_extend M4 预置 区域框选重识别结果（region_x/y/w/h + ocr_texts），级联删除
image_search FTS5 虚表 trigram 分词全局搜索，聚合 OCR/caption/tag 三源。4 个触发器自动同步（ocr 增删、caption 更新、tag 插入）
table_cache M4 预置 表格识别结果缓存（table_result JSON，按 image_id+model_tier 索引）
image_embedding M6 预置 向量元数据，每图两条：image（CLIP 图向量）/ text（BGE 文本向量）。唯一约束 (image_id, entry_type, model)
image_embedding_vec M6 · vec0 sqlite-vec 虚表 vec0(embedding float[512])。按扩展可用性在 Python 层动态创建，缺失则降级跳过
image_hash M4 预置 感知哈希去重（phash / dhash / ahash），主键 (image_id, hash_type)
image_layout 可选 DocLayout-YOLO 版面分析结果（layout_json）

五、跨切面关注点

贯穿各层的横切机制——这些是理解代码行为的隐性契约。

单实例

QLocalServer 监听 ClickOCR-SingleInstance；二次启动检测到已存连接则发 b"show" 唤醒已有实例并退出，避免双开抢占全局热键。

线程模型

4 类 QThread：OcrWorker（识别）、TableWorker（SLANet）、EngineLoader（后台加载模型）、ScrollWorker（滚屏拼接）。UI 线程全程不阻塞。

引擎容错

引擎初始化/加载失败 → engine=None + 延迟弹窗，程序继续运行：截图、贴图、标注照常可用，仅文字识别停用。

懒加载策略

ocr_keep_alive=true（默认）后台线程预加载；false 则首次识别才构建，启动省 200–400MB。模型热切换 switch_model() 只换内部引擎。

主题与文案外置

明/暗/跟随系统 + install_system_follow 运行时切换；全部 UI 文案走 ui_text.json 的 T()，缺失回退默认值；55 个 SVG 图标按需着色。

窗口配额

三类独立配额：贴图 max_history_windows=1、历史图 max_hist_windows=3、钉图 max_pin_windows=5（上限 20）。超限从最旧回收。

FloatGroup 浮窗管理

收口 z 序（raise_all）、绘制让位（maybe_yield，事件驱动替代 80ms 轮询）、位置跟随（follow）——消灭散落的手动 raise_。

NUMA 亲和（已实现）

多 NUMA 节点时把进程绑到节点 0：Windows 用 GetLogicalProcessorInformationEx + SetProcessAffinityMask/SetThreadGroupAffinity，Linux 读 /sys + sched_setaffinity。单节点零开销。

平台守卫

Windows 专属：hotkey.py（RegisterHotKey + nativeEvent）、scroll_capture.py、字体策略。跨平台：NUMA 探测、ORT EP 选择。

六、构建线与运行时矩阵

两条构建线源于 onnxruntime 包的互斥性；EP 能力按平台分化。

构建线环境 / spec产物
CUDA 版 .venv（onnxruntime-gpu 1.28.0）
ClickOCR.spec		 NVIDIA 最优 ~1.9GB
DML 通用版 .venv-dml（onnxruntime-directml 1.24.4）
ClickOCR_dml.spec		 推荐分发 462MB · ~70s
纯 CPU 版 已废弃 ClickOCR_cpu.spec 路线无效——从 gpu 包剔 CUDA 库永远得不到 DML
平台EP 选项说明
Windowscpu · cuda · dmlDML 通吃 AMD/Intel/NVIDIA DX12（WDDM 2.4+）
Linuxcpu · cuda · migraphx · openvino无 DirectML；AMD 走 MIGraphX（ROCm 6.4+），Intel 走 OpenVINO
打包版已捆绑运行时，EP 不可用即判定为设备/驱动不支持并自动回退 CPU；开发模式可 pip 自动换包。
实测参考：CUDA（v6-medium det）相对 CPU 加速 6.65×（125.7ms → 18.9ms，记录于 config.ini 的 cuda_probe）。DML 选卡经 _detect_dml_device 探测 + monkeypatch 注入 device_id 实现——因 rapidocr 的 ProviderConfig 不接受直接传 EP options，且 onnxruntime-directml 1.24.4 存在兼容问题。老显卡（如 930MX 不支持 DML）会自动跳过落到核显或 CPU。

七、当前架构风险

读代码时识别出的结构性问题，按影响程度排列。

风险等级说明与建议
core_engine 双份 高 ClickOCR/core_engine 与 E:\WorkSpace\core_engine 两份并存。自包含收益明确，但改动需同步两侧，且易出现「改了外层、打包用内层」的静默不一致。建议：明确单向同步流程，或改为构建时拷贝
版本历史缺失 高 git 仓库于 2026-08-18 意外丢失并重建，此前历史不可恢复；当前仅 2 次提交且存在未提交改动。建议立即建立「一功能一提交」粒度
app.py 过载 中 1505 行的 App 同时承担编排、落库、窗口配额、收藏同步、拖放去重等职责。建议按「窗口管理 / 持久化 / 识别调度」拆分为协作对象
超大 UI 文件 中 result_overlay.py 2209 行、annotation.py 2008 行、settings_panel.py 1390 行。标注图元已工厂化是好的，但窗口本体仍需拆分
平台耦合 中 hotkey.py 强绑 Win32 + nativeEvent，是 Linux 移植首要改造点。建议抽 HotkeyManager 抽象接口（Linux 走 X11 / GlobalShortcuts portal，Wayland 支持不一）
